Característica Plan Estimado (Ctrl+L) Plan Real (Ctrl+M+F5)
¿Ejecuta la consulta? NO SÍ

Tiempos No disponibles CPU + Elapsed reales

⚠️ Regla de Oro: Si Estimated Rows difiere mucho de Actual Rows, las estadísticas están desactualizadas. Ejecuta UPDATE STATISTICS.

🔧 Operadores de Acceso a Datos

🟢 CLUSTERED INDEX SEEK

Búsqueda directa por clave del clustered index

WHERE ClienteID = 100

🟢 INDEX SEEK

Búsqueda directa en índice non-clustered

WHERE Email = 'x@y.com'

🟡 CLUSTERED INDEX SCAN

Lee TODO el índice clustered

SELECT * FROM Tabla

🟡 INDEX SCAN

Lee TODO el índice non-clustered

WHERE Email LIKE '%@%'

🔴 TABLE SCAN

Lee TODA la tabla (heap sin índices)

Sin índice clustered

🔴 KEY LOOKUP

Volver al clustered por columnas faltantes

Índice no cubriente
💡 Regla: No todo Scan es malo, no todo Seek es bueno. Un Seek + Key Lookup en millones de filas puede ser peor que un Scan.

Complejidad O(log n) O(n)

🔑 Key Lookup: El Enemigo Silencioso

1. SQL usa índice NC para filtrar 2. Pero necesita columnas extra 3. Va al clustered por cada fila INDEX NC CLUSTERED INDEX RESULTADO ════════ ═══════════════ ═════════ ┌────────┐ ┌─────────────┐ │TipoTX │───────────────────────────▶│ * Todas las │ 10,000 filas │= Dep │ KEY LOOKUP │ columnas │ = 10,000 └────────┘ └─────────────┘ Key Lookups!

Problema:

-- Índice en TipoTransaccion solamente
CREATE INDEX IX ON TX(TipoTransaccion);

-- Consulta necesita Monto y Fecha (NO están en el índice)
SELECT TipoTransaccion, Monto, FechaTransaccion  -- ← Key Lookup!
FROM TRANSACCIONES_BANCARIAS
WHERE TipoTransaccion = 'Depósito';

Solución - Covering Index:

-- Incluir las columnas adicionales
CREATE INDEX IX ON TX(TipoTransaccion)
INCLUDE (Monto, FechaTransaccion);  -- ← Sin Key Lookup!
⚠️ Impacto: Si la consulta retorna 10,000 filas, sin covering index = 10,000 Key Lookups adicionales = miles de lecturas extra.

📈 STATISTICS IO - Métricas Clave

SET STATISTICS IO ON;
-- Ejecutar consulta
SET STATISTICS IO OFF;
Métrica Significado Objetivo
Scan count Veces que se accedió al índice/tabla Depende de la consulta
Logical reads Páginas leídas de buffer (memoria) MINIMIZAR
Physical reads Páginas leídas de disco Idealmente 0
Read-ahead reads Lecturas anticipadas (prefetch) OK si hay physical reads
💡 Consejo: Logical reads es la métrica más importante. Compara antes/después de crear índices.

⚠️ Warnings Comunes en Planes

Warning Causa Solución
⚠️ Missing Index SQL sugiere crear un índice Evaluar y crear el índice sugerido
⚠️ Implicit Conversion Tipo de dato no coincide Usar el tipo correcto en parámetros
⚠️ No Join Predicate Producto cartesiano accidental Revisar cláusulas JOIN
⚠️ Spill to tempdb Sort/Hash sin memoria suficiente Más RAM o optimizar consulta
⚠️ Residual Predicate Filtro adicional post-seek Mejorar el índice

❌ Implicit Conversion

Cuando el tipo de dato del parámetro no coincide con la columna, SQL debe convertir TODAS las filas:

-- ❌ MALO: Columna es VARCHAR pero parámetro es NVARCHAR
DECLARE @Num NVARCHAR(20) = N'CTA-001';  -- N' indica Unicode
WHERE NumeroCuenta = @Num;  -- Causa SCAN, no SEEK

-- ✅ BUENO: Mismo tipo de dato
DECLARE @Num VARCHAR(20) = 'CTA-001';  -- Sin N
WHERE NumeroCuenta = @Num;  -- Usa SEEK correctamente
⚠️ Regla: El tipo del parámetro DEBE coincidir con el tipo de la columna para usar índices eficientemente.

🏦 Aplicación Bancaria: El Reporte Lento

Escenario: El reporte de "Estado de Cuenta" tarda 850ms y necesitamos bajarlo a <100ms.

Análisis del plan revela:

  • ❌ Index Scan en CUENTAS (falta índice en ClienteID)
  • ❌ Key Lookup masivo en TRANSACCIONES
  • ❌ Sort para ORDER BY (sin índice de soporte)

Solución:

-- Índice cubriente para CUENTAS
CREATE INDEX IX_CUENTAS_ClienteID
ON CUENTAS(ClienteID)
INCLUDE (NumeroCuenta, TipoCuenta, Saldo);

-- Índice cubriente para TRANSACCIONES
CREATE INDEX IX_TX_CuentaFecha
ON TRANSACCIONES_BANCARIAS(CuentaID, FechaTransaccion DESC)
INCLUDE (TipoTransaccion, Monto, Descripcion);

Resultado: De 850ms → 45ms (mejora de 19x)

📏 Interpretación de Costos

  • El costo es una unidad abstracta (no segundos ni MB)
  • Sirve para comparar operadores dentro del mismo plan
  • Basado en estimaciones de CPU, I/O, memoria
  • Costo bajo ≠ consulta rápida (si estadísticas están mal)
💡 Siempre validar con: 
SET STATISTICS IO ON;   -- Lecturas reales
SET STATISTICS TIME ON; -- Tiempos reales
