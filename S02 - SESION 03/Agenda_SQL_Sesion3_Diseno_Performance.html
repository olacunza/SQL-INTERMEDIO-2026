1️⃣ Tipos de Datos Óptimos

Cada byte cuenta. Una tabla de 10 millones de filas con tipos incorrectos puede desperdiciar gigabytes de espacio y memoria.

Regla de Oro: Usar el tipo más pequeño que cumpla el requisito

Dato ❌ Tipo Malo ✅ Tipo Óptimo Ahorro
Edad (0-150) INT (4 bytes) TINYINT (1 byte) 75%
Cantidad productos BIGINT (8 bytes) SMALLINT (2 bytes) 75%
Monto hasta 999,999.99 FLOAT (8 bytes) DECIMAL(9,2) (5 bytes) 37% + precisión
Código país (2 chars) NVARCHAR(50) (hasta 102 bytes) CHAR(2) (2 bytes) 98%
Nombre (máx 50) NVARCHAR(MAX) (variable) NVARCHAR(50) (hasta 102 bytes) Evita LOB
Fecha sin hora DATETIME (8 bytes) DATE (3 bytes) 62%
Sí/No VARCHAR(10) (hasta 12 bytes) BIT (1 bit) ~99%

Referencia de Tamaños de Enteros

Tipo Bytes Rango Uso Típico
TINYINT 1 0 a 255 Edad, estado, tipo
SMALLINT 2 -32,768 a 32,767 Cantidades, códigos
INT 4 -2.1 mil millones a 2.1 mil millones IDs, contadores
BIGINT 8 ±9.2 x 10^18 Solo cuando INT no alcanza
⚠️ Errores Comunes:
  • NVARCHAR vs VARCHAR: NVARCHAR usa 2 bytes por carácter (Unicode). Usar solo si necesitas caracteres especiales/internacionales.
  • VARCHAR(MAX): Almacena fuera de página (LOB). Evitar para campos que tienen límite conocido.
  • FLOAT/REAL para dinero: ¡NUNCA! Tienen errores de redondeo. Usar DECIMAL.

Cálculo de Impacto

-- Tabla de transacciones: 50 millones de registros
-- Diferencia entre INT (4 bytes) y SMALLINT (2 bytes) en 3 columnas:

Ahorro por fila: 3 columnas × 2 bytes = 6 bytes
Ahorro total: 50,000,000 × 6 bytes = 300 MB

-- Esto significa:
-- ✓ 300 MB menos en disco
-- ✓ 300 MB menos en memoria (Buffer Pool)
-- ✓ Más filas por página = menos I/O
-- ✓ Índices más compactos = búsquedas más rápidas
🏦 Caso Bancario:

Una tabla de TRANSACCIONES con 100 millones de registros:

  • Cambiar DATETIME a DATE (solo fecha): ahorra 500 MB
  • Cambiar BIGINT a INT en IDs: ahorra 400 MB
  • El Buffer Pool (RAM) trabaja más eficientemente

2️⃣ SARGability (Search ARGument ABLE)

Una consulta es SARGable cuando puede usar un índice para hacer búsqueda eficiente (Index Seek). Si NO es SARGable, SQL Server debe leer TODA la tabla (Table/Index Scan).

┌─────────────────────────────────────────────────────────────────┐
│                     ¿QUÉ ES SARGABLE?                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  SARGABLE = El predicado WHERE puede usar un INDEX SEEK         │
│                                                                 │
│  ✅ WHERE Columna = valor         → Index Seek (rápido)         │
│  ✅ WHERE Columna > valor         → Index Seek (rápido)         │
│  ✅ WHERE Columna LIKE 'abc%'     → Index Seek (rápido)         │
│                                                                 │
│  ❌ WHERE FUNCIÓN(Columna) = x    → Index Scan (lento)          │
│  ❌ WHERE Columna LIKE '%abc'     → Index Scan (lento)          │
│  ❌ WHERE Col1 + Col2 = valor     → Index Scan (lento)          │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

Index Seek vs Index Scan

Aspecto Index Seek Index Scan
Cómo funciona Va directo a las filas necesarias Lee TODAS las filas del índice
Analogía Buscar página en el índice del libro Leer todo el libro para encontrar algo
Lecturas lógicas Pocas (solo lo necesario) Muchas (todo el índice)
CPU Bajo Alto
Ejemplo 3 lecturas para 10 filas 50,000 lecturas para 10 filas

Ejemplos de Consultas SARGable y No-SARGable

❌ NO SARGABLE

-- Función en columna
WHERE YEAR(FechaTransaccion) = 2025

-- Concatenación
WHERE Nombre + Apellido = 'JuanPerez'

-- Conversión implícita
WHERE CAST(CodigoCliente AS VARCHAR) = '12345'

-- LIKE con comodín al inicio
WHERE Email LIKE '%@gmail.com'

-- Negación
WHERE NOT Estado = 'Activo'

-- Operación aritmética
WHERE Precio * 1.18 > 1000

✅ SARGABLE

-- Rango de fechas
WHERE FechaTransaccion >= '2025-01-01'
  AND FechaTransaccion < '2026-01-01'

-- Columnas separadas
WHERE Nombre = 'Juan' AND Apellido = 'Perez'

-- Sin conversión
WHERE CodigoCliente = 12345

-- LIKE con comodín al final
WHERE Email LIKE 'juan%'

-- Positivo
WHERE Estado IN ('Inactivo', 'Pendiente')

-- Mover operación al otro lado
WHERE Precio > 1000 / 1.18
💡 Regla de Oro SARGable:

La columna indexada debe estar SOLA en un lado de la comparación, sin funciones ni operaciones.

✅ columna = valor
✅ columna > valor
✅ columna BETWEEN valor1 AND valor2
❌ FUNCION(columna) = valor
❌ columna + algo = valor

3️⃣ Impacto de Funciones en el WHERE

Cada función aplicada a una columna en el WHERE destruye la posibilidad de usar un índice.

Funciones Problemáticas y sus Soluciones

Función Problemática Solución SARGable
WHERE YEAR(Fecha) = 2025 WHERE Fecha >= '2025-01-01' AND Fecha < '2026-01-01'
WHERE MONTH(Fecha) = 3 WHERE Fecha >= '2025-03-01' AND Fecha < '2025-04-01'
WHERE DATEPART(dw, Fecha) = 1 Columna calculada persistida o tabla de fechas
WHERE LEFT(Codigo, 3) = 'ABC' WHERE Codigo LIKE 'ABC%'
WHERE UPPER(Nombre) = 'JUAN' Collation CI (case insensitive) o columna calculada
WHERE ISNULL(Campo, 0) = 0 WHERE Campo IS NULL OR Campo = 0
WHERE CONVERT(DATE, FechaHora) = '2025-03-20' WHERE FechaHora >= '2025-03-20' AND FechaHora < '2025-03-21'
WHERE DATEDIFF(DAY, Fecha, GETDATE()) < 30 WHERE Fecha > DATEADD(DAY, -30, GETDATE())

Ejemplo Detallado: Búsqueda por Año

❌ MAL: Función en columna

SELECT * FROM TRANSACCIONES
WHERE YEAR(Fecha) = 2025
  AND MONTH(Fecha) = 3;

-- Execution Plan: INDEX SCAN
-- Logical Reads: 125,000
-- CPU Time: 2,500 ms

✅ BIEN: Rango de fechas

SELECT * FROM TRANSACCIONES
WHERE Fecha >= '2025-03-01'
  AND Fecha < '2025-04-01';

-- Execution Plan: INDEX SEEK
-- Logical Reads: 45
-- CPU Time: 15 ms

Conversiones Implícitas (El Asesino Silencioso)

SQL Server convierte automáticamente tipos de datos, pero esto puede destruir SARGability:

-- La columna CodigoCliente es VARCHAR(10)

❌ WHERE CodigoCliente = 12345  
   -- SQL convierte TODOS los valores de la columna a INT
   -- Resultado: Index Scan

✅ WHERE CodigoCliente = '12345'
   -- No hay conversión
   -- Resultado: Index Seek
⚠️ Regla de Precedencia de Tipos:

SQL Server siempre convierte al tipo de mayor precedencia:

INT > VARCHAR → Si comparas VARCHAR con INT, convierte TODO el VARCHAR a INT

Esto significa que cada fila debe convertirse antes de comparar = SCAN.

4️⃣ Patrones Correctos para Performance

Patrón 1: Columnas Calculadas Persistidas

Cuando necesitas filtrar frecuentemente por una función, crea una columna calculada:

-- Agregar columna calculada PERSISTIDA
ALTER TABLE TRANSACCIONES
ADD FechaAnio AS YEAR(Fecha) PERSISTED;

-- Crear índice en la columna calculada
CREATE INDEX IX_Trans_FechaAnio ON TRANSACCIONES(FechaAnio);

-- Ahora SÍ es SARGable
SELECT * FROM TRANSACCIONES WHERE FechaAnio = 2025;

Patrón 2: Tabla de Fechas (Date Dimension)

-- Crear tabla de fechas
CREATE TABLE DIM_FECHAS (
    Fecha DATE PRIMARY KEY,
    Anio SMALLINT,
    Mes TINYINT,
    Dia TINYINT,
    DiaSemana TINYINT,
    EsFinDeSemana BIT,
    EsFeriado BIT
);

-- Usar con JOIN en lugar de funciones
SELECT T.*
FROM TRANSACCIONES T
JOIN DIM_FECHAS F ON T.Fecha = F.Fecha
WHERE F.Anio = 2025 AND F.Mes = 3;

Patrón 3: Búsqueda de Texto Parcial

-- Si necesitas buscar "contiene" frecuentemente:

-- Opción A: Full-Text Index
CREATE FULLTEXT INDEX ON Productos(Descripcion) 
KEY INDEX PK_Productos;

SELECT * FROM Productos 
WHERE CONTAINS(Descripcion, 'laptop');

-- Opción B: Columna calculada para prefijo
ALTER TABLE Clientes
ADD EmailDominio AS RIGHT(Email, LEN(Email) - CHARINDEX('@', Email)) PERSISTED;

CREATE INDEX IX_EmailDominio ON Clientes(EmailDominio);
🏦 Caso Bancario - Búsqueda de Transacciones: 
-- ❌ Mal: Buscar transacciones de los últimos 30 días
WHERE DATEDIFF(DAY, FechaTransaccion, GETDATE()) <= 30

-- ✅ Bien: Pre-calcular la fecha límite
DECLARE @FechaLimite DATE = DATEADD(DAY, -30, GETDATE());
WHERE FechaTransaccion >= @FechaLimite

-- ✅ Mejor aún: Parámetros pre-calculados
-- El optimizador puede estimar mejor las filas
