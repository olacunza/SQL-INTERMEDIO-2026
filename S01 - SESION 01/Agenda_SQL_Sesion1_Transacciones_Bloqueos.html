1️⃣ Propiedades ACID

Las transacciones en SQL Server garantizan las propiedades ACID:

Propiedad Significado Ejemplo Bancario
A - Atomicidad Todo o nada. Si una parte falla, todo se revierte. Transferencia: Si el débito pasa pero el crédito falla, ambos se revierten.
C - Consistencia La DB pasa de un estado válido a otro estado válido. El saldo total del banco antes y después de la transferencia es igual.
I - Aislamiento Las transacciones concurrentes no se "ven" entre sí. Dos cajeros no pueden retirar el mismo saldo simultáneamente.
D - Durabilidad Una vez confirmado (COMMIT), los datos persisten. Si el sistema cae después del COMMIT, el depósito está registrado.
🏦 Caso Bancario Real: En una transferencia interbancaria de S/. 5,000:
  1. Atomicidad: Si el Banco A debita pero el Banco B no puede acreditar → ROLLBACK total
  2. Consistencia: La suma de todas las cuentas debe ser igual antes y después
  3. Aislamiento: Mientras se procesa, nadie más puede modificar esas cuentas
  4. Durabilidad: El registro queda en el log aunque se apague el servidor

Sintaxis Básica de Transacciones

BEGIN TRANSACTION;  -- Inicia la transacción

    -- Operaciones DML aquí
    UPDATE CUENTAS SET SALDO = SALDO - 5000 WHERE CUENTAID = 101;
    UPDATE CUENTAS SET SALDO = SALDO + 5000 WHERE CUENTAID = 202;

    -- Si todo está bien
    IF @@ERROR = 0
        COMMIT TRANSACTION;  -- Confirma cambios
    ELSE
        ROLLBACK TRANSACTION; -- Revierte todo

2️⃣ Niveles de Aislamiento (Isolation Levels)

SQL Server ofrece 5 niveles de aislamiento que controlan cómo las transacciones interactúan entre sí:

Nivel Dirty Read Non-Repeatable Read Phantom Read Performance
READ UNCOMMITTED ✅ Permitido ✅ Permitido ✅ Permitido ⚡ Más rápido
READ COMMITTED (default) ❌ Bloqueado ✅ Permitido ✅ Permitido ⚡⚡
REPEATABLE READ ❌ Bloqueado ❌ Bloqueado ✅ Permitido ⚡⚡⚡
SERIALIZABLE ❌ Bloqueado ❌ Bloqueado ❌ Bloqueado 🐢 Más lento
SNAPSHOT ❌ Bloqueado ❌ Bloqueado ❌ Bloqueado ⚡⚡ (usa TempDB)

Definiciones de los Problemas

  • Dirty Read: Leer datos que otra transacción aún no ha confirmado (puede revertirse)
  • Non-Repeatable Read: Leer el mismo dato dos veces y obtener valores diferentes
  • Phantom Read: Ejecutar la misma consulta y obtener filas adicionales o faltantes
⚠️ Importante: En un sistema bancario, READ UNCOMMITTED está PROHIBIDO para operaciones financieras. ¡Podrías leer un saldo que nunca existió!

Cómo Cambiar el Nivel de Aislamiento

-- Cambiar a nivel de sesión
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- Verificar nivel actual
SELECT 
    CASE transaction_isolation_level 
        WHEN 0 THEN 'Unspecified' 
        WHEN 1 THEN 'ReadUncommitted' 
        WHEN 2 THEN 'ReadCommitted' 
        WHEN 3 THEN 'RepeatableRead' 
        WHEN 4 THEN 'Serializable' 
        WHEN 5 THEN 'Snapshot' 
    END AS IsolationLevel
FROM sys.dm_exec_sessions 
WHERE session_id = @@SPID;

3️⃣ Deadlocks (Interbloqueos)

¿Qué es un Deadlock?

Cuando dos transacciones se bloquean mutuamente esperando recursos que la otra tiene.

    Transacción A                    Transacción B
         │                                │
         ▼                                ▼
    Bloquea Tabla X              Bloquea Tabla Y
         │                                │
         ▼                                ▼
    Espera Tabla Y  ◄──────────►  Espera Tabla X
         │                                │
         └────────── DEADLOCK! ───────────┘

Ejemplo Clásico de Deadlock Bancario

-- SESIÓN 1: Transferencia de Cuenta A → Cuenta B
BEGIN TRAN
    UPDATE CUENTAS SET SALDO = SALDO - 1000 WHERE CUENTAID = 1; -- Bloquea Cuenta 1
    WAITFOR DELAY '00:00:05'; -- Simula proceso
    UPDATE CUENTAS SET SALDO = SALDO + 1000 WHERE CUENTAID = 2; -- Espera Cuenta 2
COMMIT

-- SESIÓN 2: Transferencia de Cuenta B → Cuenta A (ejecutar simultáneamente)
BEGIN TRAN
    UPDATE CUENTAS SET SALDO = SALDO - 500 WHERE CUENTAID = 2;  -- Bloquea Cuenta 2
    WAITFOR DELAY '00:00:05'; -- Simula proceso
    UPDATE CUENTAS SET SALDO = SALDO + 500 WHERE CUENTAID = 1;  -- Espera Cuenta 1
COMMIT
-- ¡DEADLOCK! SQL Server matará una de las dos transacciones.

Estrategias para Prevenir Deadlocks

Estrategia Descripción Implementación
Ordenamiento Consistente Acceder a las tablas siempre en el mismo orden Siempre bloquear primero la cuenta con ID menor
Transacciones Cortas Minimizar el tiempo de bloqueo Hacer cálculos ANTES del BEGIN TRAN
Usar ROWLOCK Bloquear solo la fila, no la página/tabla UPDATE ... WITH (ROWLOCK)
SNAPSHOT Isolation Evitar bloqueos usando versionado Activar RCSI en la base de datos
💡 Tip Senior: Siempre accede a las tablas en orden alfabético o por ID. Si todos los SPs hacen UPDATE en el mismo orden (CLIENTES → CUENTAS → TRANSACCIONES), los deadlocks se reducen drásticamente.

Detectar Deadlocks con Extended Events

-- Ver información de deadlocks recientes
SELECT 
    XEvent.query('(event/data[@name="xml_report"]/value/deadlock)[1]') AS DeadlockGraph
FROM (
    SELECT CAST(target_data AS XML) AS TargetData
    FROM sys.dm_xe_session_targets st
    JOIN sys.dm_xe_sessions s ON s.address = st.event_session_address
    WHERE s.name = 'system_health' AND st.target_name = 'ring_buffer'
) AS Data
CROSS APPLY TargetData.nodes('RingBufferTarget/event[@name="xml_deadlock_report"]') AS XEventData(XEvent);

4️⃣ NOLOCK vs READ COMMITTED SNAPSHOT (RCSI)

¿Qué es NOLOCK?

-- NOLOCK = READ UNCOMMITTED a nivel de tabla
SELECT * FROM TRANSACCIONES WITH (NOLOCK);

-- Es equivalente a:
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SELECT * FROM TRANSACCIONES;
⚠️ Peligros de NOLOCK:
  • Dirty Reads: Puedes leer datos que se van a revertir
  • Datos Duplicados: Puede leer la misma fila dos veces
  • Datos Faltantes: Puede saltarse filas durante un split de página
  • Datos Inconsistentes: Leer mitad de una fila actualizada

¿Qué es READ COMMITTED SNAPSHOT (RCSI)?

Es una configuración a nivel de base de datos que permite lecturas sin bloqueos, pero leyendo la última versión confirmada de los datos.

-- Activar RCSI (requiere acceso exclusivo a la DB)
ALTER DATABASE MiBancoDB SET READ_COMMITTED_SNAPSHOT ON;

-- Verificar si está activo
SELECT name, is_read_committed_snapshot_on 
FROM sys.databases 
WHERE name = 'MiBancoDB';

Comparación NOLOCK vs RCSI

Característica NOLOCK RCSI
Dirty Reads ✅ Sí (peligroso) ❌ No
Bloquea escritores ❌ No ❌ No
Usa TempDB ❌ No ✅ Sí (Version Store)
Requiere cambio en código ✅ Sí (cada query) ❌ No (a nivel DB)
Apto para Banca ❌ NO ✅ SÍ
🏦 Recomendación Bancaria:
  • Reportes históricos: RCSI es perfecto (datos ya confirmados)
  • Consulta de saldo en cajero: RCSI con transacciones cortas
  • NOLOCK: Solo para dashboards de monitoreo donde no importa la precisión exacta
  • Operaciones críticas: Usar READ COMMITTED o SERIALIZABLE clásico

Monitorear el Version Store (RCSI)

-- Ver uso del Version Store en TempDB
SELECT 
    SUM(version_store_reserved_page_count) * 8 / 1024 AS [Version Store MB]
FROM sys.dm_db_file_space_usage;

-- Ver transacciones que generan versiones
SELECT 
    DB_NAME(database_id) AS DatabaseName,
    transaction_id,
    elapsed_time_seconds
FROM sys.dm_tran_version_store_space_usage
WHERE elapsed_time_seconds > 60; -- Más de 1 minuto
