⚠️ Regla de Oro sobre Hints

Los hints ANULAN la inteligencia del Query Optimizer.

Usar hints es el ÚLTIMO RECURSO. Primero intentar:

  1. Crear/mejorar índices
  2. Reescribir la consulta
  3. Actualizar estadísticas
  4. Solo entonces: considerar hints

🔗 JOIN Hints

Fuerzan el tipo de JOIN físico que usará SQL Server:

LOOP JOIN

Nested Loops: Outer pequeño + índice en inner

INNER LOOP JOIN

HASH JOIN

Build hash table: Sin índices, tablas grandes

INNER HASH JOIN

MERGE JOIN

Merge sorted: Ambos lados ordenados

INNER MERGE JOIN 
-- Ejemplo: Forzar LOOP JOIN
SELECT c.Nombre, cu.NumeroCuenta
FROM CLIENTES c
INNER LOOP JOIN CUENTAS cu ON c.ClienteID = cu.ClienteID
WHERE c.ClienteID BETWEEN 1 AND 100;

📋 TABLE Hints

Hint Efecto Riesgo
NOLOCK Lee sin locks (dirty reads) 🔴 Datos incorrectos
READPAST Salta filas bloqueadas 🟡 Omite filas
UPDLOCK Lock de actualización al leer 🟡 Más bloqueos
INDEX(nombre) Fuerza índice específico 🟡 Plan subóptimo
FORCESEEK Fuerza Index Seek 🟡 Plan subóptimo
FORCESCAN Fuerza Index Scan 🟡 Plan subóptimo 
-- Sintaxis
SELECT * FROM Tabla WITH (hint1, hint2) WHERE condicion;

-- Ejemplos
SELECT * FROM CUENTAS WITH (NOLOCK) WHERE TipoCuenta = 'Ahorro';
SELECT * FROM TX WITH (INDEX(IX_TX_Fecha)) WHERE Fecha > '2024-01-01';

⚠️ NOLOCK: Riesgos Reales

NOLOCK permite lecturas "sucias". Puede causar:

  • Dirty Reads: Leer datos que luego se revierten
  • Filas Duplicadas: Por page splits durante lectura
  • Filas Faltantes: Por reacomodos de páginas
  • Datos Parciales: Leer fila mientras se actualiza

❌ NUNCA usar para: Saldos, auditoría, inventario crítico

✅ Aceptable para: Reportes aproximados, dashboards de tendencias

⚙️ OPTION Clause

Se coloca al FINAL de la consulta y afecta toda la ejecución:

RECOMPILE

Genera nuevo plan en cada ejecución

OPTION (RECOMPILE)

OPTIMIZE FOR

Optimiza para valor específico

OPTION (OPTIMIZE FOR (@var = 500))

OPTIMIZE FOR UNKNOWN

Usa distribución promedio

OPTION (OPTIMIZE FOR UNKNOWN)

MAXDOP

Limita CPUs (1=serial)

OPTION (MAXDOP 1)

FORCE ORDER

JOINs en orden escrito

OPTION (FORCE ORDER)

USE PLAN

Usa plan XML específico

OPTION (USE PLAN 'xml...')

🐛 Parameter Sniffing

EL PROBLEMA DEL PARAMETER SNIFFING Primera ejecución: Ejecuciones posteriores: ══════════════════ ════════════════════════ EXEC sp_Buscar @ID = 1 EXEC sp_Buscar @ID = 999999 │ │ ▼ │ ┌─────────────────┐ │ │ Compila plan │ │ │ optimizado para │ │ │ @ID = 1 │◄─────────────────────────┘ │ (pocas filas) │ USA EL MISMO PLAN! └─────────────────┘ (puede ser TERRIBLE)

Síntomas:

  • SP rápido a veces, lento otras (con mismos parámetros)
  • DBCC FREEPROCCACHE "arregla" temporalmente
  • Rendimiento errático e impredecible

💊 Soluciones para Parameter Sniffing

Solución Ventaja Desventaja
OPTION (RECOMPILE) Plan siempre óptimo CPU extra cada ejecución
OPTIMIZE FOR (@var = x) Un solo compile Elegir valor "típico"
OPTIMIZE FOR UNKNOWN Usa promedios No siempre óptimo
Variables locales Simple Puede empeorar estimados
Query Store Force Sin cambiar código Mantenimiento 
-- Solución 1: RECOMPILE
SELECT * FROM TX WHERE Tipo = @Tipo OPTION (RECOMPILE);

-- Solución 2: OPTIMIZE FOR valor típico
SELECT * FROM TX WHERE Tipo = @Tipo OPTION (OPTIMIZE FOR (@Tipo = 'Normal'));

-- Solución 3: Variables locales (menos recomendado)
DECLARE @LocalTipo VARCHAR(20) = @Tipo;
SELECT * FROM TX WHERE Tipo = @LocalTipo;

📊 Query Store

Sistema integrado (SQL 2016+) para monitorear y estabilizar planes:

1

Captura consultas y planes automáticamente

→
2

Almacena métricas de rendimiento

→
3

Permite forzar planes específicos

→
4

Detecta regresiones

-- Habilitar Query Store
ALTER DATABASE BancoDB SET QUERY_STORE = ON;

-- Forzar un plan específico  
EXEC sp_query_store_force_plan @query_id = 1, @plan_id = 2;

-- Quitar forcing
EXEC sp_query_store_unforce_plan @query_id = 1, @plan_id = 2;
💡 Consejo: Query Store es la forma más limpia de estabilizar planes sin modificar código. Ideal para aplicaciones legacy o cuando no tienes acceso al código fuente.

📝 Plan Guides

Aplican hints sin modificar el código fuente:

-- Crear Plan Guide para un SP
EXEC sp_create_plan_guide
    @name = N'PG_MiSP',
    @stmt = N'SELECT ... consulta exacta ...',
    @type = N'OBJECT',
    @module_or_batch = N'dbo.MiStoredProcedure',
    @params = NULL,
    @hints = N'OPTION (RECOMPILE)';

-- Ver Plan Guides
SELECT * FROM sys.plan_guides;

-- Eliminar
EXEC sp_control_plan_guide @operation = N'DROP', @name = N'PG_MiSP';

⚡ MAXDOP - Control de Paralelismo

MAXDOP 1 (Serial)

  • Consultas OLTP pequeñas
  • Alta concurrencia
  • Evita overhead de paralelismo

MAXDOP > 1 (Paralelo)

  • Consultas analíticas grandes
  • Procesamiento batch
  • Reportes pesados
-- OLTP: Sin paralelismo
SELECT * FROM Ordenes WHERE ID = @ID OPTION (MAXDOP 1);

-- Reporte: Paralelismo completo
SELECT Region, SUM(Total) FROM Ventas GROUP BY Region OPTION (MAXDOP 0);

🏦 Caso Práctico: Estabilizando el Core Bancario

Escenario: El SP de "Consulta de Movimientos" es crítico pero inestable. A veces 50ms, otras 15 segundos.

Diagnóstico:

  • Parameter sniffing: Clientes pequeños vs grandes
  • Plan variable según primer parámetro compilado

Solución implementada:

  1. Habilitar Query Store para monitorear
  2. Identificar el mejor plan (menor avg_duration)
  3. Forzar ese plan con sp_query_store_force_plan
  4. Alternativa: OPTION (RECOMPILE) para casos extremos

Resultado: Rendimiento estable: 80-120ms consistente
